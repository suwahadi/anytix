# Fase 3 — Hari-H Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A paid buyer gets one QR per person on `/orders/{uuid}` and in a PDF, gate staff scan it in a PWA with a full green or red screen, the admin runs vouchers (CRUD, bulk generator, usage) that buyers apply through "Lebih hemat pakai promo", and the panel gains the sales dashboard, CSV export, identity reveal with audit, 60-day identity retention, admin accounts and the audit log viewer. k6 scripts ship for Fase 4.

**Architecture:** Quota and voucher counters stay in the Fase 0 plpgsql engine. Fase 3 adds two engine functions (`check_in_ticket`, `reissue_ticket_tokens`), a retention function on pg_cron, thin admin Route Handlers over small services in `src/lib/admin/` and `src/lib/catalog/`, a PDF route, the scanner page, and voucher UI on both sides.

**Tech Stack:** Next.js 16.4 (cacheComponents, partialPrefetching), postgres.js, zod 4, `qrcode` (installed), `pdf-lib` (new), `barcode-detector` ponyfill (new, loaded only without native `BarcodeDetector`), vitest, k6 scripts.

**Spec:** `PRD.md` §13, §14, §15, §16, §20, §21 + `docs/superpowers/specs/2026-10-17-anytix-mvp-design.md` §2–§4 (design doc wins on conflict). Builds on Fase 0–2 plans; read `docs/superpowers/HANDOFF.md` first.

## Global Constraints

- Everything in the Fase 0–2 Global Constraints still applies (AGENTS.md comments, no AI attribution in commits, plpgsql rules, lock order `ticket_inventory → holds → orders → vouchers`, `transaction()` not `sql.begin`, `adminRoute` for every admin API with audit rows for every mutation, Next.js 16 rules, antislop during the work with dials ENERGY 1 / RHYTHM 2 / MOTION 1, `cursor: pointer` on every link, button and tab).
- QR (PRD §15, design doc §3.1): the payload is `tickets.token` (128-bit base64url, 22 chars) and nothing else. Never put buyer data, identity or order ids in a QR.
- Identity numbers (PRD §14): masked `3201********0001` in panel, PDF, CSV, scanner and logs; full value only through the audited reveal. Never in job payloads, audit `diff`, API responses outside the reveal route, or console output.
- Check-in is online and atomic: one `update tickets … where checked_in_at is null and status = 'valid' returning` decides; every scan, accepted or not, writes `checkin_events`.
- Scanner copy fixed by the PRD: green shows buyer name, ticket category, "Tiket {seq} dari {n}", masked identity when present; red shows "SUDAH DIPAKAI pukul {HH:mm}, Gate {gate}" or "TIDAK VALID".
- Voucher rules (PRD §13, design doc §3.4): discount on ticket subtotal only, tickets after discount ≥ Rp1.000, percent rounded down, one voucher per order, code case-insensitive and unique per event, empty `max_uses` = unlimited, scoped vouchers count only matching categories. `compute_quote` already implements this; Fase 3 does not change the formula.
- Promo UI copy: button "Lebih hemat pakai promo"; a bad code shows its message inside the modal and the buyer can still pay without a voucher (PRD §8).
- CSV cells that start with `=`, `+`, `-`, `@`, tab or CR are prefixed with `'`; files start with a UTF-8 BOM; times are in the event timezone as `YYYY-MM-DD HH:mm`.
- Nothing in this phase may run the worker against real recipients while `admin@admin.com` is still an active admin (HANDOFF trap).

## Review Focus

1. Two gates scan the same QR within the same second: exactly one green, the other red "SUDAH DIPAKAI" (Task 6 test `parallel scans of one ticket give one valid`).
2. A QR from another event, a voided or reissued token, or random text from a non-ticket QR is scanned: red "TIDAK VALID", a `checkin_events` row, and no 500 (Task 6 tests `wrong event is rejected`, `old token after reissue is invalid`, `garbage token is invalid`).
3. The last voucher use is taken between quote and checkout: checkout answers 409, the page drops the promo, re-quotes and keeps the buyer on step 3 with the message in view (Task 4 test `checkout with exhausted voucher is 409` plus the browser step).
4. A buyer name with characters outside WinAnsi (for example "Đặng" or an emoji) reaches the PDF: the PDF still renders (Task 5 test `pdf survives non latin names`).
5. An admin types `=HYPERLINK(...)` as a form answer or a buyer name contains `+62…`: the CSV cell is neutralised (Task 9 test `csv neutralises formula cells`).
